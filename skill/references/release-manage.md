# Delete or replace one release/tag

Read gitrelease.md, common.md and release-publish.md. This is an explicit exception to ordinary publication's no-deletion/no-retagging rule, not a cleanup step or push-error workaround. It remains part of gitrelease, with no additional command or automatic version bump.

## Select exact scope

- `gitrelease delete --tag TAG [--delete-scope release|tag|both]`: default scope is both. Release means the matching GitHub Release and its attached assets; tag means that exact remote and local tag. Never delete a same-named branch. Never infer the latest/previous tag as a deletion target: ask for an exact tag if missing. Allowed additional selectors are --remote and --component; reject bump/version/from/build-number/branch/route/workflow/draft/assets/replacement flags for this action.
- `gitrelease publish --replace-existing`: replace only the tag derived from the prepared committed app version and verified prefix (or a consistent explicit --tag), plus its matching Release if present. Never delete an older, differently named version to publish a new version. Reject this flag on init/prepare/delete; an omitted action does not authorize replacement. An explicit inspection-only request remains read-only, without backups, downloads, fetches or mutations.
- Normal publish does not delete or replace anything. Missing selected objects are already absent, not permission to select another version. A fully absent target makes replacement ordinary publication with no deletion. If the existing tag/release already matches the approved new SHA, notes and assets, report completion or resume only missing publication work; do not delete it again unless the user explicitly requests a fresh replacement of that inspected matching state. Independently released backend products remain outside this scope.

## Inspect, preserve and obtain the concrete decision

1. Resolve the supported app, exact owner/repo and remote, selected tag, local/remote tag object IDs and peeled commit SHAs, matching Release ID/URL, draft/prerelease/immutable status, asset IDs/names/sizes, protection and permissions. Validate refs/paths as structured inputs; reject symbolic tag refs rather than following them to another ref. A failed lookup is not proof of absence; require verified not-found results. A local/remote mismatch must be listed separately. Check relevant queued/running publishers and deletion/release event triggers that could recreate or act on the target. Do not silently cancel runs or disable workflows; propose the exact intervention if necessary.
2. Check immutability before destructive work. GitHub allows deleting an immutable Release, but its tag name cannot be reused afterwards; block same-tag replacement before deletion. Tag-only deletion is blocked while such a Release exists. Offer a new version or retain/defer; never bypass protection, change immutability settings or promise restoration of that tag name.
3. For replacement, finish all ordinary publication preflight first: committed approved SHA, version/changelog, valid app assets or verified workflow build/publication gates, available auth, chosen route, and normal branch push readiness. Missing assets/credentials or divergent branch history block replacement before any deletion. When branch push is needed and authorized, complete and verify the ordinary branch push before deleting the existing Release/tag. Stop on rejection; do not use -f, rebase, merge or amend implicitly. The --replace-existing flag authorizes no branch rewrite.
4. Before any deletion, create a verified local recovery record outside the worktree. Preserve exact local and remote tag objects and commits under unique create-only refs/git-workflow-backup/ refs; fetch only the selected missing objects if needed and authorized, without overwriting a local tag. Save Release metadata/title/body/status and the asset manifest; when deleting a Release, download all attached assets to validated noncolliding local paths and verify size plus provided digest or record local SHA-256. Never print credentials, upload the backup, stage it or push backup refs. A failed/incomplete backup blocks deletion. Plan remains read-only; prepare backups only for the explicit delete/replace action.
5. Show the concrete old tag object/commit and Release/assets to remove, new SHA/notes/platform assets and route for replacement, impact on existing download links/clients, backup location, and exact operation sequence. Backups preserve content, not original Release IDs, download counters, attestations or a guarantee of full restoration. Offer feasible choices with benefit/consequence/scope and one evidence-based Rekomendasi. For an already distributed stable version moving to different code, normally recommend a new patch/version over replacement; retain/defer is viable. The user may deliberately choose replacement when allowed. Obtain approval for the exact destructive scope if not already concretely authorized; do not repeat an approval covering the inspected unchanged state. A bare flag or generic prior request does not approve unknown asset loss.

## Execute as checked stages

1. Re-read tag objects, Release ID/body/status/assets and publisher state immediately before deletion. If they changed, stop and revise the proposal. API deletion and Git push are separate operations; do not claim an atomic transaction.
2. If Release deletion is selected and it exists, delete that exact Release via supported GitHub tools/API or structured argv `gh release delete TAG --repo OWNER/REPO --yes`, only after approval. Do not use --cleanup-tag: handle the tag separately with its inspected object ID. Verify the Release is absent before continuing. Deleting a Git tag alone does not delete its Release; deleting a Release without cleanup does not delete its tag.
3. If tag deletion is selected and the remote tag exists, conditionally delete only `refs/tags/TAG`, pinned to the inspected remote tag object ID (not its peeled commit): structured argv equivalent to `git -c push.followTags=false push --force-with-lease=refs/tags/TAG:OLD_REMOTE_OID REMOTE :refs/tags/TAG`. This lease is solely a guard on the selected tag deletion, not branch force-push permission. If the tag changed or deletion is rejected, stop; never refresh the expected OID and retry blindly. Verify remote absence. Delete a selected existing local tag with compare-and-delete `git update-ref --no-deref -d refs/tags/TAG OLD_LOCAL_OID`, preserving a concurrently changed ref. Absent refs are skipped, not errors to mask.
4. For delete, verify the requested final state and that out-of-scope refs/releases remain untouched; stop here. For replacement, recheck approved new SHA/metadata and remote absence, create an annotated tag at that SHA without -f, and push only that tag with explicit refspec and expected absence (`--force-with-lease=refs/tags/TAG:`). Disable push.followTags. The create-only guard prevents silently replacing a concurrently recreated tag; on collision stop. Then use the single approved workflow/direct publisher and verify actual app assets under release-publish.md. Do not repeat a branch push that already succeeded.
5. Inspect every exit status/result and final state; record completed stages and old/new state in the local recovery record. Stop subsequent dependent steps on failure. Report exactly what remains deleted, local/pushed/new, pending or failed, with backup and the unfinished retry stage. Never automatically roll back a tag, re-delete a newly created replacement or create duplicate releases. Restoration is a separate reviewed request subject to current remote state and immutable-name restrictions. Retrying publication inspects the recovery record and resumes the new matching tag/release; it does not start deletion again merely because --replace-existing was used before.

## One request and semicolon previews

`gitrelease publish` and `gitrelease publish --replace-existing` are each one agent request. A user may paste a semicolon-separated Git sequence as intent; parse the requested targets/actions as data, apply the same gates and show any additional release-deletion scope. Never eval or shell-run the input verbatim. Semicolons may be used in a clearly labeled one-line operation preview after values are verified, but they do not imply failure gating or authorization.

Execute separate structured argv calls with checked results. If a shell artifact is explicitly requested, generate guarded commands appropriate to the actual shell: a Bash/compatible chain uses &&; PowerShell native commands need explicit $LASTEXITCODE checks or supported equivalent. Never emit an unguarded destructive `cmd1; cmd2; ...` as a runnable one-shot script. Do not describe the sequence as atomic. All steps already covered by concrete authorization proceed in one run; unresolved required decisions pause only their dependent steps.
