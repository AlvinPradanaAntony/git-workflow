# gitrelease

Read `common.md`, `release-targets.md`, `versioning.md`, `changelog.md` and `release-publish.md`. Use `messages.md` for a release preparation commit and `push.md` before a branch push. This invocation manages the current project; a request to add or review this command does not authorize publishing the reference repository.

For delete or --replace-existing, also read release-manage.md before acting. One invocation orchestrates checked sequential operations; a semicolon-separated user sequence is intent to inspect, not shell code to execute verbatim.

For init, also read release-init.md. It sets up local version/changelog plus the selected build/packaging/release automation; no implicit commit, tag, push or CI dispatch.

Scope: every project type except a website/browser-only web product. Apply release-targets.md to classify the selected product by entrypoints, codebase, manifests, existing CI and distribution policy, not by language, lack of GUI or the presence of HTTP. CLI/tools/installers, scripts, libraries/packages/SDKs, independently distributed services/backends, mobile/desktop apps and source-distributed projects are supported. Electron/Tauri desktop apps are supported even when they use web technologies. A website and its exclusively website-bound release/deployment stay outside scope. In a mixed repository, select the non-web component; ask if the boundary is materially ambiguous. Missing build config is a setup/readiness issue, not automatic out-of-scope. Projects distributed as scripts/source need no invented compiler or executable asset.

## Actions and options

`gitrelease <init|prepare|publish|delete>`. If the action is omitted, show these actions and their boundaries without repo inspection or mutation; do not infer a mutating action. Reject unknown actions before any mutation; do not silently alias them to prepare.

| Action | Boundary |
| --- | --- |
| `init` | Validate/initialize project version and changelog, create or complete selected packaging/build/release workflow and project helpers under release-init.md. Follow clear project conventions automatically; resolve material choices only. Preserve an existing version unless replacement was selected. Local setup only. |
| `prepare` | Inspect current Git/codebase changes, version/changelog and pipeline readiness; infer the appropriate version, resolve material ambiguities, then update authorized local version/changelog files. No implicit staging, commit, tag, push or CI dispatch. |
| `publish` | Publish the approved, committed release version and verified product-appropriate distribution outputs at a verified SHA by the chosen workflow or direct GitHub route. Do not bump the version again on a retry. |
| `delete` | Delete one exact --tag with --delete-scope release, tag or both (default both), after preservation and concrete scope approval. No version edits, branch push or replacement publication. |

Accept `--version VERSION` OR `--bump patch|minor|major`; `--from TAG_OR_SHA`; `--component PATH`; `--build-number N`; `--remote NAME`; `--branch NAME`; `--tag NAME`; `--route auto|workflow|direct` (auto); `--workflow PATH` (init may create a verified new path under .github/workflows; other actions require an existing workflow); `--draft`; `--assets PATH...` (direct route only). Version may include a SemVer prerelease suffix such as `2.0.0-rc.1`. Derive prerelease state from the selected version. Do not invent a stable release for a prerelease version. A repository's tag prefix may differ from `v`.

Accept --replace-existing only for publish. Accept --delete-scope release|tag|both only for delete, with required --tag (ask for the exact target when absent); delete accepts only --tag, --delete-scope, --remote and --component. Follow release-manage.md for flag restrictions, backup, approval, immutable-name constraints and resume behavior. The installer --replace is unrelated to release replacement.

Reject conflicting selectors, unknown options, unsafe refs/paths, `--assets` on a workflow route, and unsupported draft/prerelease combinations before mutation. In init/prepare publication flags can describe the future route but never execute it.

## Prepare: inspect, decide and update locally

1. Inspect the selected non-web product, operation state, actual staged/unstaged/eligible untracked changes, committed changes since the verified relevant release baseline, version authority/derived fields, changelog and existing packaging/publisher. Follow versioning.md; do not classify a bump from commit prefixes or file counts alone. A scoped fetch is allowed only when needed and authorized to resolve missing history; no push or workflow dispatch.
2. Derive major/minor/patch from actual compatibility and behavior using the established policy. A clear recommendation is applied under prepare's local-write authorization without an extra routine decision menu. An explicit --version/--bump is validated against project/native constraints; surface a material contradiction rather than silently choosing another version. If a manifest/changelog already represents this preparation, reuse it and update only missing exact-version notes/linked fields; do not bump again on a repeat. If there is no meaningful releasable change, retain the version and report no change.
3. Ask a specific evidence-based question only when scope, conflicting versions, compatibility, prerelease promotion, build-counter policy or another material decision cannot be resolved. Wait for the dependent edits. Independent inspection/validation already authorized may continue; never select a version or distribution target indirectly while that choice is unanswered.
4. Check workflow/signing/selected-asset requirements and report publication blockers. Missing yet-to-be-built binaries or CI credentials do not by themselves block unambiguous local metadata preparation. Missing setup is handled through init or a separate authorized scoped fix; prepare does not invent a new workflow each release. Never claim ready-to-publish from metadata checks alone.
5. Update only the selected product's authoritative and proven derived version fields and exact-version changelog entry, preserving unrelated changes/history. Validate agreement and report old/new version, classification evidence, edited files, actual checks and publication blockers. Preserve existing staging; do not stage or commit code or release files implicitly. commitmsg and publish are separate commands unless already explicitly authorized.

An explicit user request for inspection or a draft only remains read-only regardless of the action name: show the proposed preparation without edits, staging, fetch, builds, commit, tag, push or dispatch. This respects the user's narrower intent; it is not a separate action or flag.

## Interactive decisions

Derive decisions and recommendations from current repository evidence, explicit arguments and prior authorization; the decision examples below are not a fixed questionnaire. Do not ask about routine choices already determined by a consistent project pattern, such as the version authority, changelog path, tag prefix, existing packaging targets or matching publisher. Apply those conventions within the requested action and report the choice with evidence. A convention identifies how to act; it does not authorize an extra commit, remote write, changed release scope or stability claim.

Ask only when a material ambiguity remains or the next action needs authorization not already given: for example contradictory version sources, uncertain compatibility, multiple eligible components/publishers without a selection, changing distribution targets, or a release commit/tag/publication outside the approved scope. Explicit --version/--bump or an unambiguous project policy can resolve the local version choice; do not ask again merely because patch/minor/major options exist. For prepare, infer and apply an evidence-backed local version when compatibility and project policy are clear; do not ask a routine patch/minor/major question.

1. Apply the scope check first. Show the selected non-web product/components, authoritative version fields, relevant latest tag/release, baseline range, pending code versus committed code, changelog path/style, release workflow triggers, selected distribution mode and applicable OS/architectures, expected outputs or verified source-distribution policy, and concrete mismatches. Do not ask information already resolved from the repo. Init/prepare may proceed before assets are built, but publish requires the asset checks in release-publish.md.
2. Ask a specific question naming the unresolved decision and actual versions, components, files, targets or route. Explain why repository evidence or existing authorization cannot resolve it. Present 2–4 feasible options in a table: **option**, **benefit**, **consequence**, **exact files/remote scope**. Mark exactly one **Rekomendasi** and explain its reason using the actual diff and release state. Include **Pertahankan kondisi sekarang / Tunda** when leaving things unchanged is viable. Do not pad the menu with irrelevant platforms, impossible routes or canned patch/minor/major choices. Apply this format to every decision menu, including optional follow-up actions; omit an unnecessary menu rather than listing unexplained alternatives. Do not recommend publishing when validation is incomplete.
3. Typical unresolved decisions may include initializing versus finishing an already prepared version; compatibility/version policy; reconciling contradictory versions; choosing a monorepo component; an unapproved release commit or publication; competing publishers; or a pipeline change versus defer. Batch at most three decisions. Wait for an answer before the dependent action; elapsed time, silence and a recommendation are not consent. Continue independent work already authorized by the requested action, such as inspecting an unrelated approved target or validating already approved metadata, only if it cannot predetermine the unanswered choice or exceed the requested action boundary. If the decision is a prerequisite, state exactly which edits, builds, commit, tag or publication are blocked and what can still proceed. Use the host's question tool only for choices it supports; ask required approval directly when that tool is not permitted for approvals.
4. After authorized local preparation, make the exact version/changelog diff reviewable and report actual validation. If a release commit was not already authorized, offer it, retaining local changes, or deferring. If committing is chosen, select only approved release files and preserve all unrelated staged/unstaged work. Stop the commit if their isolation is ambiguous; independent authorized inspection may continue. Never bulk-stage or unstage other work or silently include arbitrary code changes in the release commit.
5. Before publication, finish the reviewable work and show owner/repo, target branch/SHA, version/tag, release title/notes, asset list, route and validation. Explain whether pushing this tag publishes immediately through Actions; a tag push is a publication decision in such a repo. Obtain the missing concrete publication decision. Prior explicit authorization for this exact state is sufficient; do not ask again unless the state or scope changes.

## Execute and report

- Use the version/changelog and publication references as the execution contract. If the tree or SHA changes, rebuild the proposal and reconsider authorization for the changed scope.
- Preserve changelog history. Initial setup must not fabricate past release dates or achievements; continuation must not rewrite previously published release content except an explicitly reviewed replacement under release-manage.md.
- Report action, old/new version and applicable build numbers, exact edited files, commit status, tag/SHA, route, workflow run, release URL/draft/prerelease state, attached assets and actual validation. Distinguish prepared files, local commit, pushed tag, running workflow and verified published release. A pushed tag alone is not release success.
- On failure, report the last successful stage and precise retry action. Do not re-bump, re-commit, retag, delete published tags or duplicate a release as an automatic retry. Explicit delete/replacement follows release-manage.md and resumes only unfinished approved stages.
