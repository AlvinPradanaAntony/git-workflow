# Git Workflow

For `$git-workflow help` or `/git-workflow help`, read `references/help.md`: default compact numbered catalog with separate description and options/value columns; `--detailed` (or `detailed`) shows numbered detailed sections; `--cmd` without a value lists all 12 numbered Git command names; `--cmd NUMBER_OR_NAME` shows only the selected command detail. Validate help selectors and never execute the selected command or inspect Git. For a Git command, read `references/common.md` and then exactly the matching command reference below. All 12 Git actions are contained in this skill. The command name may follow `$git-workflow` or `/git-workflow`, or appear in the user's task text after this skill has been selected. Normalize `/commitplan` to `commitpln`. Never treat a preview-only request as authorization to commit, reset or push. If no command or intent can be identified, summarize available choices and ask only for the missing intent.

Default language is English. Standard format is subject, blank line and `- ` bullets without a Changes label. For `commitmsg` without an explicit `--format`, exactly one changed file in the repository selects short; otherwise select standard. `--lang both` means one EN and ID message separated by a blank-line-delimited `---`, with shared trailers once at the end. User instructions always control preview versus execution. `commitpln` is read-only; `commitmsg` commits locally without push.

Codex CLI/IDE explicitly invokes this as `$git-workflow commitmsg --lang both`; ChatGPT can select `Git Workflow` then pass `commitmsg --lang both`. Antigravity invokes `/git-workflow commitmsg`. The installer creates no short workflow aliases. Codex's native custom slash registration is not implied by a skill; a textual `/commitmsg` is recognized only if the host passes it to the agent.

For `gitrelease`, read `references/release-targets.md` and identify the released product from its codebase and distribution conventions. Support all project types except website/browser-only web products, including CLI, scripts, installers, tooling, libraries, services, mobile, desktop and source-distributed projects. Do not reject a CLI because it has no GUI, or a library/script because it has no executable build. For mixed repos select the non-web release component; ask only if the boundary is unclear. Inspect its version/changelog/build or packaging pipeline before offering options. For init, read `references/release-init.md` and create/complete local version, changelog, selected packaging/build/release workflow and project helpers; use unambiguous conventions without blanket approval and ask only material unresolved choices. For prepare, inspect Git changes, infer the version from actual compatibility and behavior, check changelog/pipeline readiness, then update local metadata within the clear authorized scope. Omitted action shows usage without repo inspection or mutation; reject unknown actions rather than aliasing them. Explain each option's benefit, consequence and exact scope, mark one **Rekomendasi** with evidence, and offer retain/defer when viable. Derive routine choices from verified project conventions; ask specific questions only for unresolved material choices or missing authorization. Wait only on dependent actions and continue independent authorized work within the requested action. Prepare the concrete files/notes before the publication decision; do not duplicate approval for an already authorized exact release state. Use `scripts/release_notes.py` to extract only the approved changelog version and optional one predecessor. Use one request for checked sequential publication; semicolon previews are not executable authorization. For delete or publish --replace-existing, read `references/release-manage.md`, preserve the exact old state and obtain any missing concrete destructive approval; never force-push a branch. Require the verified distribution outputs appropriate to the selected product; source distribution with no compilation is valid when supported by codebase conventions or an explicit choice. Missing required outputs block publication; absence of an unnecessary native build does not. Match build/test commands, toolchains and targets to repository evidence, and ask only material unresolved decisions; never assume the TonzToon reference is the target repo.

For local/global installation, updates, removal or diagnostics, read `references/installation.md`. Prefer the standalone `git-workflow` CLI: `init` installs into the Git root detected from the terminal's current directory, including subfolders and linked worktrees; `init -g` chooses the current user. CLI init/update/uninstall apply immediately unless `--dry-run` is specified. This terminal CLI manages skill installation, while the agent command `gitrelease init` prepares a project's release system. Keep the existing 12 Git commands and help unchanged. Retain `scripts/install_git_workflow.py` as a migration fallback; without --project it detects the Git root from the current working directory and still needs --apply to write. Never copy an installer into a project merely to select its destination. Preserve manifest-owned files, exact backups and unrelated AGENTS.md content. Do not run Git actions or install a toolchain on the user's computer when only skill installation was requested.
