# Initialize app versioning, packaging and release automation

Read gitrelease.md, versioning.md, changelog.md and release-publish.md. Apply only to a verified mobile/desktop application. init means local release setup, not git init, CI dispatch, a store upload or a GitHub publication.

## Scope and authorization

An explicit gitrelease init authorizes local creation/update of the app's version metadata, changelog, necessary packaging configuration, project helpers and build/release workflow within a scope determined by verified repo conventions or user choices. When that scope is unambiguous, do the work and present the resulting diff; do not ask a blanket permission question to create the workflow. Do not commit, push, create tags, dispatch jobs, provision runners, install tools globally, create signing keys, write remote secrets or change store/deployment settings implicitly.

Separate scaffolding from release readiness. Config files can be prepared without executing a full native build; report what has and has not been validated. Run existing scoped non-publishing validators when available. A missing credential is a blocker to a signed build/publication, not a reason to invent a key or report a placeholder workflow as ready.

## Inspect and resolve only material choices

1. Apply the product scope check first. A website alone is not converted into a desktop product. Verify native/app entrypoints, target folders, packaging tool/dependencies, build scripts, manifests/lockfiles/toolchain versions, current CI, signing configuration and distribution conventions. init may supply missing packaging config for an already verified app; missing packaging is not proof that a website is an app.
2. Identify the authoritative app version and linked fields, changelog path, tag convention, release components, current runners, supported OS/architectures and expected installer/portable files. Reuse existing repo versions, build counters, dependency managers and scripts. Do not silently reset an established version/counter or change backend API versions merely because they coexist.
3. Keep an existing complete matching workflow and packaging config; fill only verified gaps. Default --route auto prefers the existing publisher, or creates a GitHub build/release workflow when no publisher exists and app scope is clear. Explicit --route workflow creates/adapts that route. Explicit --route direct prepares local packaging/version/changelog and documented build requirements without adding a competing automatic publisher; if an existing automatic publisher would run for the same tag, resolve its reviewed bypass/disable scope before calling direct publication ready. --workflow may identify a new .github/workflows/*.yml or *.yaml path for init; it must resolve to an existing workflow for prepare/publish. Default to the existing relevant path or an unused .github/workflows/build-release.yml; never overwrite an unrelated same-named file.
4. Derive platforms and formats from a consistent documented distribution policy/configuration; ask only when multiple materially different targets are plausible. Do not turn every framework-supported OS into a release target. If the app has no distribution selection, present feasible choices and a recommendation rather than silently enabling all platforms. For iOS, decide actual IPA signing/distribution, not an unsigned archive labeled installable. Native code folders alone do not establish signing readiness.
5. Explain unresolved decisions with actual evidence, benefit/consequence/exact scope and one Rekomendasi; include retain/defer where viable. Examples: Android only versus signed Android+iOS when iOS distribution is unconfigured; existing Windows portable scope versus adding supported Linux/macOS; competing publishers; signing policy; or changing an existing trigger. Naming a new file or following an established package format is routine. Wait only on dependent setup; approved version/changelog/helper work may proceed independently without predetermining the unanswered platform choice.

## Create concrete local setup

- Initialize/update version metadata and the changelog under their contracts; preserve existing history and formatting outside approved changes. An existing valid app version may be retained during setup. Initial notes describe verified capabilities, not invented past releases or placeholder achievements.
- Reuse verified build/packaging commands. When config/scripts are missing, add the minimal project-owned config using the already chosen toolchain and actual app entrypoint/resources. Do not introduce another packaging framework, upgrade dependencies or run a publish-capable version command as hidden housekeeping. Additional dependencies or architecture changes need a concrete scope choice when not already authorized. Do not add dead jobs, commented template matrices, unused secrets or dummy outputs for excluded targets.
- Generate jobs only for selected real targets. Adapt the runner/toolchain and outputs to the project rather than copying TonzToon's Flutter jobs: Android signed APK; iOS distributable signed IPA; Windows installer/portable; Linux package/portable; macOS installer/app bundle. Each selected OS/architecture has exact build command, output path, filename, required signing inputs and checks. Cross-platform desktop support includes portable formats when supported/selected; never assert all platforms compile without validation.
- Resolve prerequisite secret names from project conventions and the selected signing/distribution method. Refer to required secrets through CI without embedding values. Fail explicitly when a required secret or signing output is missing; do not silently fall back to debug/unsigned builds or skip a required platform while publishing the rest. If signing/distribution choices are unresolved, report the dependent jobs as blocked rather than writing a guessed final pipeline. Provide concrete setup requirements; never request secret values in chat.
- Make every extraction/validation helper CI-owned in the project. Reuse an appropriate tracked helper, or copy this skill's standalone scripts/release_notes.py to a nonconflicting project scripts path; include that file in the local setup diff. No references to a global or installed skill path on a runner. Use the helper's actual --changelog and --version arguments; wrap the extracted exact-version notes in the body required by changelog.md. The helper alone is not a complete Release body.

## Workflow contract

1. Use actual project paths and checked commands. Default a new automatic workflow to the verified release-tag pattern; validate the exact tag/version inside the job before a build/publication. Do not publish on every branch push or pull request. Reuse existing triggers when suitable; changing their publication behavior is a material choice. If adding workflow_dispatch, verify its selected ref/input semantics and prevent duplicate publishers for the same tag.
2. Validate app version/tag/changelog agreement and nonempty exact-version notes before building. Respect prerelease and platform-native version rules. Follow the established monotonically valid build-counter authority; do not assume a newly created workflow's run_number exceeds previously distributed counters. When no valid allocation is known, resolve that policy before claiming readiness.
3. Build from the checked-out release SHA, using project toolchain versions and lockfile-preserving dependency commands. Keep required app resources and signing inputs scoped. Use current official documentation for the selected framework/actions when needed; only generic queries leave the repo. Do not guess obsolete action versions or allow dependency-install commands to also publish packages/tags.
4. Upload/download only exact expected app outputs with unique target/architecture names. Configure missing outputs as errors (for example upload-artifact if-no-files-found: error) and explicitly check nonempty app files, correct target/version and signing/distribution properties. A wildcard file list or an artifact directory listing alone is not the publication gate. Source archives/checksums alone are not app assets.
5. The publisher depends on every required validation/build job and fails before creating/publishing a Release if any selected app output is missing/invalid. Never use continue-on-error, an always() publisher or optional job skipping to hide failed required targets. Log-only summary/cleanup steps may use always() without publication. Validate the final asset set against the selected platform map; attach only those approved files.
6. Generate the exact-version Indonesian notes plus the required Apa yang Baru/Download layout, real filenames and distribution limits under changelog.md. Infer prerelease from a validated SemVer prerelease identifier, including alpha and other suffixes, not only beta/rc; build metadata alone is not prerelease. Respect the selected draft/stable/prerelease mode and immutable-release rules. Workflow and direct publication must not race.
7. Grant minimal permissions, with contents: write only to the publisher if needed. Prevent overlapping publishers for the same tag using a suitable concurrency group or equivalent repo convention; do not cancel an active publication automatically. Never bypass protected environments or replace an existing published tag/Release as workflow cleanup; explicit replacement remains governed by release-manage.md.

## Validate and finish

Check manifest/packaging syntax, workflow syntax and cross-job outputs/needs, selected matrix and runners, exact version extraction, asset-missing failure behavior, references to actual local helper paths, and diff consistency. Use actionlint or repo validators when available; do not claim a syntax parse proves native builds, secrets, signing or CI execution. Include a scoped full build only when requested or required by an already authorized validation policy and the environment supports it; avoid unexpected toolchain downloads just for init.

Report old/new (or retained) version, changelog, workflow and packaging/helper files; platforms, formats, expected output names; trigger/draft/prerelease behavior; required external setup; tests actually run and remaining blockers. Distinguish local setup prepared, signing/runner setup pending, build untested and publication ready. Offer a separate scoped commit only if needed; never commit/tag/push from init itself.

For later updates, prepare uses this established pipeline and updates the version/changelog, not a new workflow every release. If a gap is discovered, present the concrete missing setup and resolve it through init or a scoped approved fix. prepare includes change inspection, evidence-based version selection and readiness checks before editing local metadata; material questions pause only dependent work. Routine releases use prepare, commitmsg, then publish. An explicit inspection-only request stays read-only.
